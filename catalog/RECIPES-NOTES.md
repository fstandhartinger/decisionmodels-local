# Install recipe coverage and limits

Recipes added here are source-derived and remain `verified.status: unverified`; no server, package install, model download, GPU, or third-party code was run for this slice. Every process binds to loopback, and installer-managed model processes must receive `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` without an HF token.

## Non-standard API shapes

- `h2o-lightning-4b`, `imajev-4b`, `neohorse-jev-4b` (text), `torchcast-decision-12b`, and `xor-26b-a4b` expose the TypeSafe `/v1/systemone` request/response shape. Imajev accepts JSON image data through that same route.
- `surogate-rune-26b-a4b-v3` exposes the same typed-decision body at `/v1/decisions`. Benchmark Heaven routed it through a helper proxy that changed only the path to `/v1/systemone` and mapped HTTP 400 to 422. The schema can point `proxy_jev` at `/v1/decisions`, but it has no setting for the status mapping.
- NeoHorse text requests use `/v1/systemone`; the recipe sets `image_path` to null because its image request needs a single top-level `image` data URL and exactly one question. A gateway translation from the normal multimodal request to that field is required; `proxy_jev` does not imply that translation is implemented.
- Shisa-de-1 serves OpenAI-style `/v1/completions`, not TypeSafe. Benchmark Heaven rendered the decision scaffold, requested one generated token with logprobs, and summed option-letter logprobs at the answer slot. This uses the schema-supported `letter_logprobs` mode; exact vLLM package pins for the benchmarked row were not recovered, and prompt rendering/probability extraction require a supported prompt configuration.
- Jev-Omni and Quyet were benchmarked through in-process adapters and do not have an author HTTP endpoint. Each needs a reviewed Jev-compatible wrapper; no wrapper was invented here.

## Variants without `install`

- `autojev-27b`: the BH recipe copied a reviewed local-only `model.py` variant alongside the upstream author server. The schema can pin the upstream commit archive but cannot carry that reviewed local file, so a recipe using only unmodified author code would not reproduce the measured runtime. Its CPU variant also lacks a pinned portable stack.
- `bobcat-flash-1.2`: BH's server command and `vllm==0.30.0` are known, but the remaining serving packages were unversioned and the recorded run did not retain their resolved freeze. The schema permits exact package pins only.
- `decider-12b`: the GPU Dockerfile pins Torch and Transformers, but resolves flash-linear-attention, NumPy, huggingface-hub, Jinja2, FastAPI, Uvicorn, and HTTPX against a date cutoff without a retained exact freeze. The schema has no resolver-cutoff field. CPU/MPS author instructions do not pin a separate stack either.
- `decisio-gemma-4-31b-v080`: the author repository's `uv.lock` is the source of the frozen environment, but the recipe schema cannot execute `uv sync --frozen`; the repo's codeload archive is also larger than the small code archives used for `code[]` pins. No approximate package set was substituted.
- `deck31b`: the author server loads the frozen Gemma checkpoint by Hub repo ID and pinned revision, with no model-path CLI option. The recipe schema has no way to place catalog weights into that exact Hub cache layout while keeping the server offline.
- `imajev-4b` GPU: Benchmark Heaven built a custom Dockerfile from the pinned PyTorch CUDA base image, installed exact direct dependencies, and added locally compiled CUDA kernels. The recipe schema cannot build Docker layers or reproduce those generated kernel wheels, so the base image alone is insufficient. CPU, MPS, and MLX are also undocumented as exact stacks: the optional dependencies are ranges (apart from `mlx-vlm==0.7.1`) and the source has no lockfile the executor can consume.
- `jev-omni`: the measured `JevOmniLocalAdapter` is an in-process adapter, not an HTTP server. The author's separate server path downloads additional Gemma components and is not the BH readout.
- `jevify-gemma4-26b-a4b`: the author endpoint is Jev-compatible, but the BH runtime/version was not recovered. The author lockfile is not directly executable through the current recipe schema, and portable dependency resolution cannot be expressed as exact pins.
- `jpt-4b`: `llm2jev` exposes TypeSafe, but the GPU runtime used for this row is marked unverified and its exact vLLM pins were not recovered. No guessed serving stack was added.
- `neohorse-jev-4b` GPU: the local evidence lacks the actual BH launch command/flags; the model-card vLLM deployment instructions alone do not prove what BH ran. The documented CPU and MPS native server variants are installable.
- `neohorse-jev-4b` GGUF variants: the author runtime exposes a Python prediction API, not an HTTP server; a Jev-compatible wrapper is still needed.
- `quyet-1-0-large`: BH used an in-process adapter around the author library. The documented author CLI is batch-oriented and does not expose the gateway endpoint.
- `reflex-4b`: the measured stable configuration is pinned to `231f896d`, while the available BH Dockerfile stack belongs to a different LoRA configuration and code commit. Reusing it would change the model. The stable commit has `uv.lock`, but the executor schema cannot consume it with `uv sync --frozen`.
- `rene-1-31b-fp8`: the BH serving shim is an external job-local file, not an author weight-repo script or a code archive at the model's pinned source commit. The exact adapter source is not representable by the allowed recipe fields.
- `shisa-de-1`: the exact vLLM build/pins for the BH row were not recovered. Its `letter_logprobs` API mode is expressible by the recipe schema, but prompt rendering/probability extraction need the gateway prompt configuration.
- `surogate-rune-26b-a4b-v3`: the benchmarked intake recipe used the pinned Surogate v1.5.3 wheel and Torch 2.11.0+cu130. The captured install output shows Transformers 5.19.0, but no complete dependency freeze was retained. Its launcher also builds `LD_LIBRARY_PATH` dynamically from the venv's `site-packages/nvidia/*/lib`; this schema cannot express that runtime-derived library path. The author endpoint is TypeSafe-shaped at `/v1/decisions`, though the benchmark helper also mapped HTTP 400 to 422.
- `torchcast-decision-12b`: Benchmark Heaven wrapped the digest-pinned vLLM base image in a custom image with its own entrypoint, adapter files, and runner. The recipe schema can pin the base image but cannot override a Docker entrypoint per process or represent the measured wrapper image digest; launching the shim from the base image would be incorrect.
- `test-tiny`: this is a hidden installer smoke-test fixture, not a benchmark model; no author/BH model-serving provenance exists.

The Surogate wheel requires glibc 2.39 or newer (Ubuntu 24.04/Noble) and CUDA 13; its schema recipe is omitted because the dependency freeze and dynamic library path are not expressible. The XOR bundle expects Docker Engine, NVIDIA Container Toolkit, and Docker Compose v2.40 or newer on the host. These host prerequisites should be checked by the executor before it starts the XOR recipe.
